## 1. 设计原则

### 1.1 大道至简：先基础版，后增强版（2026-10-13 决定）

**只建"现在就要用"的表。** 判断一张表该不该现在建，问三个问题：

1. 不建它，这次的功能能不能做？（能 → 先不建）
2. 它有独立的查询需求吗（单独 join / 排序 / 统计）？（没有 → 先不建）
3. 以后加回来的成本高吗？（低 → 晚点加）

三条里前两条只要有一条是"能/没有"，就先不建。之所以敢这么砍，是因为
**repo 层把 SQL 关在了一个地方**（见 §6）：加一张表 = 新增一个 repo 文件 + 一个迁移版本，
接口层和 service 层不用动。

反过来说，"大道至简"不是少写代码，而是**把变化关在一个地方**。

### 1.2 板端硬约束（决定了技术选型）

| 约束 | 影响 |
| --- | --- |
| 离线，apt / pip 不可用，新依赖要预置 aarch64 wheel | 只用标准库 `sqlite3`，**不引入 ORM、不引入 Alembic** |
| 单机、低并发（一个人用一个终端） | 无需连接池；短连接 + 事务即可 |
| 断电是常态 | 开 WAL、写入原子、备份要能恢复 |
| 板载 eMMC 寿命有限 | 控制写入频率（草稿防抖 800ms）、日志轮转 |
| 知识图谱在 Neo4j | 业务库**不复制**图谱内容，只存报告引用到的节点 id 与摘要 |

### 1.3 命名与类型约定

| 约定 | 说明 |
| --- | --- |
| 表名 | 单数名词、小写下划线：`account`、`report`、`audit_log` |
| 时间列 | `_at` 后缀，值 `YYYY-MM-DDTHH:MM:SS`（本地时间） |
| 日期列 | `_on` 后缀，值 `YYYY-MM-DD` |
| 布尔列 | `INTEGER` 0/1 |
| JSON 列 | `_json` 后缀，JSON 文本（UTF-8，不转义中文） |
| 主键 | **雪花 ID**：`id INTEGER PRIMARY KEY`（不带 `AUTOINCREMENT`，应用生成），见 §5 |
| 外键 | 显式声明并开 `PRAGMA foreign_keys=ON`；**审计表例外**（见 §4.5） |

### 1.4 JSON 的使用边界

JSON 只用于**整存整取的文档内容**，且必须满足"永远一起读、一起写"：

- 适用：报告的抬头全量字段、66 条填写内容、风险评定值映射、导出文件记录。
- 不适用：需要筛选 / 排序 / 统计的字段 —— 一律提升为真实列
  （如 `client_name`、`report_no`、`assessed_on`、`status`）。

理由：SQLite 查 JSON 要用 `json_extract`，写起来别扭、索引也弱。
**凡会出现在查询条件里的字段，都不许留在 JSON 里。**

### 1.5 数据库级 PRAGMA（写进取连接函数）

```sql
PRAGMA journal_mode = WAL;      -- 断电更安全，读写不互斥
PRAGMA synchronous  = FULL;     -- 板端断电频繁，宁可慢一点也不丢已提交数据
PRAGMA foreign_keys = ON;       -- 外键真的生效（SQLite 默认是关的）
PRAGMA busy_timeout = 10000;    -- 等锁 10 秒，避免瞬时 500
PRAGMA temp_store   = MEMORY;
```

## 2. 现状盘点

现有库只有 4 张表，都是跟着旧版单文件前端临时长出来的：

| 现有表 | 问题 |
| --- | --- |
| `users` | 缺工号、首登改密、停用时间与操作者 |
| `sessions` | 缺 `last_seen_at`（做不了空闲超时） |
| `report_history` | 只有"提交后的结果"，**没有状态机、没有报告编号、没有风险评定值与得分等级** |
| `form_draft` | **每人只能有一份**，跨电梯复用 —— 这正是旧版"上一条电梯的判定被误当本次结果"的根源 |

所以 v1 不是补两张表，而是按报告全生命周期重构：
一条 `report` 从草稿走到归档，`report_history` 与 `form_draft` 都并进它。

## 3. 表清单

### 3.1 基础版：5 张表

| # | 表名 | 一句话 |
| --- | --- | --- |
| 1 | `account` | 谁在用（单角色：检验员） |

### 3.2 砍掉的表，以及它们去了哪

砍不等于丢，每一项都有明确去向：

| 原计划表 | 去向 | 说明 |
| --- | --- | --- |
| `schema_version` | **SQLite 自带的 `PRAGMA user_version`** | 一个整数就够，不必建表 |
| `login_attempt` | **内存计数** | 重启清零；终端场景足够，不再建表 |
| `password_history` | 不做（P1 再说） | 记住最近 3 次口令不是刚需 |
| `report_unfit` | 需要统计时再加 | 可从 `items_json` 全量重算，加回成本低 |
| `report_file` | 并入 `report.files_json` | 导出记录永远按报告查，单独建表没必要 |
| `app_config` | **继续用 `.env`** | 配置界面留到 P1；编号前缀、机构名等都是部署期设定 |
| `config_history` | 随配置界面一起做 | 真要查历史，`audit_log` 里已有 `config_update` |
| `item_catalog_version` | **启动时现算** | 读 `jte_items.json` + 算哈希，由 `/api/system/info` 返回 |

### 3.3 什么时候把它们加回来

| 触发条件 | 加什么 |
| --- | --- |
| 要做统计报表（不符合项分布 / 检验员工作量） | `report_unfit`（投影表，可从 JSON 重算） |
| 要配置界面 | `app_config` + `config_history` |
| 安全要求提高（比如设备要交给外单位） | `login_attempt`、`password_history` 落库 |
| 要按导出文件反查报告 | `report_file`（或先给 `files_json` 加表达式索引） |

## 4. 表结构详设

### 4.0 报告的两套标识（先说清楚）

| 标识 | 字段 | 例子 | 用途 | 用户可见 |
| --- | --- | --- | --- | --- |
| 内部主键 | `id`（雪花 ID，64 位整数） | `532918374650120192` | 表间关联、接口路径 `/api/reports/{id}` | 否 |
| 业务编号 | `report_no`（TEXT） | `GDSEI-JTE-20261013-001` | 印在报告上、归档、口头引用 | 是 |

1. **草稿阶段还没有编号** —— 编号在"生成报告"时才分配，而主键必须一建记录就有。
2. **机构可能改编号规则**，已发出的报告要保住旧号，主键不能随规则变。
3. **作废号不复用** → 业务编号天然断号；主键不断号，做索引与外键更省事。

内部主键之所以用雪花 ID 而不是 1、2、3（**2026-10-13 定案**）：

1. **为多台终端留路**：自增 id 一上第二台必撞号，届时改号或合并库都是手术。
2. **应用侧生成，插入前就有 id**：便于"先建报告再挂明细"，接口重试天然幂等。
3. **不可枚举**：自增 id 会泄露"一共做过多少份报告"。

代价与对策（两条都要落进实现，见 §5）：板端 RTC 不可信 → id 内时间戳**不当业务时间用**，
并用 `MAX(id)` 反推时间戳作下界防回拨；雪花 ID 超出 JS 安全整数 → **JSON 里 id 一律用字符串**。

界面呈现：已生成 / 已归档显示 `report_no`；草稿没有正式编号，显示「草稿 · 创建时间」，
链接仍用 id，不把 id 当编号展示给用户。

### 4.1 `account` —— 账号

```sql
CREATE TABLE IF NOT EXISTS account (
  id                   INTEGER PRIMARY KEY,           -- 雪花 ID
  username             TEXT    NOT NULL,              -- 登录名，创建后不可改
  display_name         TEXT    NOT NULL,              -- 姓名，进报告与留痕
  employee_no          TEXT    NOT NULL DEFAULT '',   -- 工号（可空）
  password_salt        TEXT    NOT NULL,
  password_hash        TEXT    NOT NULL,
  password_algo        TEXT    NOT NULL DEFAULT 'pbkdf2_sha256$120000',
  role                 TEXT    NOT NULL DEFAULT 'inspector',  -- 恒为 inspector，预留扩展
  is_active            INTEGER NOT NULL DEFAULT 1,
  must_change_password INTEGER NOT NULL DEFAULT 0,
  created_at           TEXT    NOT NULL,
  created_by           INTEGER REFERENCES account(id),  -- 首次初始化时为 NULL
  last_login_at        TEXT,
  disabled_at          TEXT,
  disabled_by          INTEGER REFERENCES account(id)
);

CREATE UNIQUE INDEX IF NOT EXISTS ux_account_username ON account(username);
CREATE INDEX        IF NOT EXISTS ix_account_active   ON account(is_active);
```

要点：

1. `username` 唯一且**不可修改** —— 历史报告的责任人要能对上。
2. **只停用不删除**（真删除要满足"无报告"，由 service 校验）。
3. `password_algo` 存"算法 + 迭代次数"，将来提高强度可渐进升级，不必一次重算所有人。
4. `role` 恒为 `inspector`：单角色是当前决定，字段留着将来不必改表。

### 4.2 `session` —— 登录令牌

```sql
CREATE TABLE IF NOT EXISTS session (
  token        TEXT    PRIMARY KEY,        -- secrets.token_urlsafe(32)
  account_id   INTEGER NOT NULL REFERENCES account(id) ON DELETE CASCADE,
  created_at   TEXT    NOT NULL,
  expires_at   TEXT    NOT NULL,
  last_seen_at TEXT,                       -- 空闲超时用
  origin       TEXT    NOT NULL DEFAULT '' -- 来源（本机 / 局域网），供审计
);

CREATE INDEX IF NOT EXISTS ix_session_account ON session(account_id);
CREATE INDEX IF NOT EXISTS ix_session_expires ON session(expires_at);
```

1. 改密、停用、重置口令 → 删除该账号全部会话（`ON DELETE CASCADE` 兜住删账号）。
2. 空闲超时：`last_seen_at` 超过 `session_idle_hours` 视为过期；登录与启动时顺带清理。
3. **不做"内存态会话"**：一体机重启后强制重新登录虽然安全，但现场体验差；
   而且"改密即踢下线"要靠持久化才可靠，所以这张表留着。

### 4.3 `report` —— 报告主表

```sql
CREATE TABLE IF NOT EXISTS report (
  id              INTEGER PRIMARY KEY,                 -- 雪花 ID
  report_no       TEXT,                                -- 草稿为 NULL，生成时分配
  status          TEXT    NOT NULL DEFAULT 'draft',    -- draft|generated|filed|void
  version         INTEGER NOT NULL DEFAULT 1,          -- 每次重新生成 +1
  created_by      INTEGER NOT NULL REFERENCES account(id),
  created_at      TEXT    NOT NULL,
  updated_at      TEXT    NOT NULL,
  generated_at    TEXT,
  exported_at     TEXT,
  voided_at       TEXT,
  void_reason     TEXT    NOT NULL DEFAULT '',

  -- 抬头里需要筛选/排序的字段，从 JSON 提升为真实列
  client_name     TEXT    NOT NULL DEFAULT '',         -- 委托单位名称
  user_name       TEXT    NOT NULL DEFAULT '',         -- 使用单位名称
  device_category TEXT    NOT NULL DEFAULT '',         -- 设备类别
  product_no      TEXT    NOT NULL DEFAULT '',         -- 产品编号
  location        TEXT    NOT NULL DEFAULT '',         -- 安装地点
  assessed_on     TEXT    NOT NULL DEFAULT '',         -- 评估日期 YYYY-MM-DD

  -- 内容（整存整取）
  form_json       TEXT    NOT NULL DEFAULT '{}',       -- 抬头 21 个字段全量
  items_json      TEXT    NOT NULL DEFAULT '[]',       -- 66 条填写内容
  counters_json   TEXT    NOT NULL DEFAULT '{}',       -- {total,done,unfit,missing}
  risks_json      TEXT    NOT NULL DEFAULT '{}',       -- { "1.7": RiskValue }
  files_json      TEXT    NOT NULL DEFAULT '[]',       -- 导出记录（原 report_file 表）
  score           INTEGER,                             -- 综合安全状况得分 G
  grade           TEXT,                                -- 一级/二级/三级/四级
  narrative       TEXT    NOT NULL DEFAULT '',         -- 叙述性文字
  provenance_json TEXT    NOT NULL DEFAULT '{}',       -- 图谱链路/规则命中/是否用模型/耗时

  -- 追溯
  catalog_version TEXT    NOT NULL DEFAULT '',         -- 生成时使用的条目库版本
  template_version TEXT   NOT NULL DEFAULT ''          -- 如 JTE-09-R02-3.00
);

CREATE UNIQUE INDEX IF NOT EXISTS ux_report_no      ON report(report_no) WHERE report_no IS NOT NULL;
CREATE INDEX        IF NOT EXISTS ix_report_created ON report(created_at DESC);
CREATE INDEX        IF NOT EXISTS ix_report_status  ON report(status, created_at DESC);
CREATE INDEX        IF NOT EXISTS ix_report_creator ON report(created_by, created_at DESC);
CREATE INDEX        IF NOT EXISTS ix_report_client  ON report(client_name);
CREATE INDEX        IF NOT EXISTS ix_report_on      ON report(assessed_on);
```

状态与字段的对应（service 层必须保证一致）：

| 状态 | `report_no` | `generated_at` | `exported_at` | 说明 |
| --- | --- | --- | --- | --- |
| `draft` 草稿 | 可空 | 空 | 空 | 只保存填写内容 |
| `generated` 已生成 | 必填 | 必填 | 空 | 已算出风险评定值与 G |
| `filed` 已归档 | 必填 | 必填 | 必填 | 已导出（`files_json` 非空） |
| `void` 已作废 | 保留原值 | 保留 | 保留 | `void_reason` 必填，编号不复用 |

要点：

1. **草稿保存全部状态**（抬头 + 66 条勾选 + 情形 + 其他文字）—— 2026-10-13 决定。
   旧版"不保存勾选"是为了绕开"每人一个全局草稿槽跨电梯复用"，现在一份评估一条记录，
   新建评估 = 插入空白记录，问题从模型上消失。
2. 已生成的报告被修改 → `status` 回落 `draft`、`version + 1`；旧风险值保留在
   `risks_json` 里直到重新生成覆盖（便于对比"改了什么"）。
3. 6 个提升列是 `form_json` 的**投影**，保存时由同一个 repo 方法一起写，
   禁止只改 JSON 不改列。
4. `files_json` 元素形如
   `{"fmt":"pdf","filename":"…","path":"…","size":123456,"sha256":"…","at":"…"}`。

### 4.4 `report_no_seq` —— 按日编号流水

```sql
CREATE TABLE IF NOT EXISTS report_no_seq (
  day      TEXT    PRIMARY KEY,        -- YYYYMMDD
  last_seq INTEGER NOT NULL DEFAULT 0
);
```

编号规则（2026-10-13 定）：`{机构前缀}-{YYYYMMDD}-{3 位流水}`，默认前缀 `GDSEI-JTE`
（`.env` 里的 `report_no_prefix`），例：`GDSEI-JTE-20261013-001`。

取号必须在一个事务里完成，否则会撞号：

```sql
BEGIN IMMEDIATE;
  INSERT INTO report_no_seq(day, last_seq) VALUES (:day, 0)
    ON CONFLICT(day) DO UPDATE SET last_seq = last_seq + 1;
  SELECT last_seq FROM report_no_seq WHERE day = :day;
  UPDATE report SET report_no = :no, status = 'generated', generated_at = :now WHERE id = :id;
COMMIT;
```

为什么保留这张只有 2 列的表：如果改成"取当天最大编号 + 1"，一旦当天最后一份报告被删，
编号就会被重复分配；而"作废号不复用"是机构要的硬规则。2 列换掉一整类重号 bug，值。

### 4.5 `audit_log` —— 审计日志

```sql
CREATE TABLE IF NOT EXISTS audit_log (
  id          INTEGER PRIMARY KEY,            -- 雪花 ID
  at          TEXT NOT NULL,
  actor_id    INTEGER,                        -- 故意不加外键，见下
  actor_name  TEXT NOT NULL DEFAULT '',       -- 冗余快照
  event       TEXT NOT NULL,                  -- 见 §7.3
  target      TEXT NOT NULL DEFAULT '',       -- 账号名 / 报告编号 / 配置键
  before_json TEXT,
  after_json  TEXT,
  result      TEXT NOT NULL DEFAULT 'ok',     -- ok | fail
  note        TEXT NOT NULL DEFAULT ''

CREATE INDEX IF NOT EXISTS ix_audit_at    ON audit_log(at DESC);
```

两条刻意为之：

1. **`actor_id` 不加外键**：删账号不能带走审计记录；同时冗余 `actor_name`，
   账号改名或停用之后，日志里仍是当时那个名字。
2. **只追加**：界面不提供删除入口；保留 30 天后归档为文件（见 §10.2）。

## 5. ID 生成：雪花算法

### 5.1 位分配

| 位 | 段 | 值域 | 说明 |
| --- | --- | --- | --- |
| 1 | 符号位 | 恒 0 | 保证正数 |
| 41 | 毫秒时间戳 | 相对自定义纪元 | 41 位 ≈ 69 年 |
| 10 | 工作节点 id | 0~1023 | 一台终端一个值（`.env` 的 `worker_id`，默认 1） |
| 12 | 同毫秒序号 | 0~4095 | 单节点每毫秒 4096 个，远超本系统需要 |

自定义纪元 `EPOCH_MS = 1767225600000`（2026-01-01 00:00:00 +08:00）。

### 5.2 时钟回拨与重启保护（本项目的重点）

板端 RTC 不可信（开机会回到 2021-01-01），所以必须假设"时钟会乱跳"。三道防线：

1. **启动时用库里最大 id 反推时间戳作下界**：id 里编码了时间戳，
   `last_ms = (MAX(id) >> 22) + EPOCH_MS`。即使开机时钟是 2021 年，
   生成器也从"上次发到哪儿"继续往前 —— **这是最关键的一道**。
2. **运行期小幅回拨**（≤5 ms）：等一会儿再发。
3. **运行期大幅回拨**：抛错拒绝生成，提示校时。宁可让报告生成失败（可重试），
   也绝不发重复 id。

**id 里的时间戳不参与任何业务时间**：报告时间一律看 `created_at` /
`generated_at` / `assessed_on`；报告编号走 `report_no`（按日流水），与雪花 id 无关。

### 5.3 参考实现（标准库，无第三方依赖）

```python
"""雪花 ID 生成器。板端零依赖：只用 threading + time。"""
import threading
import time

EPOCH_MS = 1767225600000
WORKER_BITS, SEQ_BITS = 10, 12
WORKER_SHIFT = SEQ_BITS
TIME_SHIFT = SEQ_BITS + WORKER_BITS
SEQ_MASK = (1 << SEQ_BITS) - 1


class Snowflake:
    def __init__(self, worker_id: int, last_ms: int = 0) -> None:
        if not 0 <= worker_id < (1 << WORKER_BITS):
            raise ValueError("worker_id 必须落在 0~1023")
        self.worker_id = worker_id
        self._lock = threading.Lock()
        self._last_ms = last_ms
        self._seq = 0

    def next_id(self) -> int:
        with self._lock:
            now = int(time.time() * 1000)
            if now < self._last_ms:
                gap = self._last_ms - now
                if gap > 5:
                    raise RuntimeError("系统时间被回拨，拒绝生成 ID，请先校时")
                time.sleep(gap / 1000)
                now = int(time.time() * 1000)
            if now == self._last_ms:
                self._seq = (self._seq + 1) & SEQ_MASK
                if self._seq == 0:
                    while now <= self._last_ms:
                        now = int(time.time() * 1000)
            else:
                self._seq = 0
            self._last_ms = now
            return ((now - EPOCH_MS) << TIME_SHIFT) | (self.worker_id << WORKER_SHIFT) | self._seq


def restore_last_ms(max_id: int | None) -> int:
    """启动时从库里最大 id 反推上次时间戳，避免时钟回拨造成重复 id。"""
    return 0 if not max_id else (max_id >> TIME_SHIFT) + EPOCH_MS
```

接入：进程启动时对各业务表取 `MAX(id)` 的全局最大值 → `restore_last_ms` → 构造单例，
放在 `repo/ids.py`；所有 `INSERT` 显式带 id。

### 5.4 传输与序列化约定（不做这条一定出 bug）

雪花 ID 是 19 位十进制数，**超出 JS 的 `Number.MAX_SAFE_INTEGER`**，浏览器里会失真
（`532918374650120192` 变成 `...200`，再去请求就是 404）。

| 层 | 类型 |
| --- | --- |
| Python | `int`（原生大整数） |
| SQLite 列 | `INTEGER`（64 位，可直接做主键） |
| **JSON / 接口** | **string**（`{"id": "532918374650120192"}`） |
| 前端 | 当字符串用，禁止 `Number(id)` |

### 5.5 验收（写进测试）

1. 单线程连续生成 100 万个不重复；8 线程 × 10 万不重复。
2. 同毫秒序号递增、跨毫秒时间戳递增。
3. 时间往前调 1 小时 → 抛错，而不是发重复 id。
4. 记录最大值后模拟时钟回到 2021 年重启 → 新 id 必须大于旧最大值。
5. 接口返回的 `id` 是字符串，能原样用于 `GET /api/reports/{id}`。

## 6. repo 数据访问层（本设计的重点）

### 6.1 分层

```text
api（路由 + 参数校验）
  └─ service（业务规则 + 事务边界）
       └─ repo（SQL，唯一允许出现 SQL 的地方）
            └─ db.py（连接 + PRAGMA + 事务上下文）
```

三条硬规矩：

1. **SQL 只允许出现在 `repo/` 目录里**，其它地方出现 SQL 字符串就算违规。
2. `service` 不 import `sqlite3`，只调 repo。
3. `api` 不 import repo，只调 service。

### 6.2 目录结构

```text
backend/app/repo/
  __init__.py
  base.py          连接、PRAGMA、事务上下文、row → dict
  ids.py           雪花 ID 单例 + 启动恢复（restore_last_ms）
  account_repo.py
  session_repo.py
  report_repo.py
  audit_repo.py
```

### 6.3 repo 做什么、不做什么

| 做 | 不做 |
| --- | --- |
| 单表增删改查、按条件查询、计数 | 业务规则校验（如"最后一个启用账号不能停用"） |
| JSON 列的序列化与反序列化 | 跨表业务编排（如"生成报告"要同时写 report + audit） |
| 把 snake_case 的列转成上层的 dict | 拼报告编号（service 拿到流水号后自己拼） |
| 提供取号原语 `next_seq(day) -> int` | 决定状态机怎么流转 |

一句话：**repo 是"数据的手"，不是"业务的大脑"。**

### 6.4 事务

1. repo 方法**自己不开启事务**；需要事务的场景由 service 用 `with db.transaction():` 包裹。
2. 单条写入如果被 service 直接调用而没开事务，`db.transaction()` 允许被隐式调用
   （写法上统一：写操作一律在事务里，读操作随意）。
3. 报告生成、编号分配、备份恢复这三处**必须**在一个事务里完成。

### 6.5 命名与返回约定

| 形式 | 约定 |
| --- | --- |
| 读单条 | `find_by_id(id) -> dict | None`、`find_by_username(name) -> dict | None` |
| 读多条 | `list_xxx(...) -> tuple[list[dict], int]`（行 + 总数） |
| 写 | `insert(...) -> dict`、`update(id, **fields) -> bool`、`delete(id) -> bool` |
| 返回类型 | **普通 dict**，不返回 `sqlite3.Row`（避免底层类型泄漏，也方便测试替换） |
| 字段名 | 与列名一致（snake_case），JSON 列的解析在 repo 内完成 |

### 6.6 各 repo 的方法清单

```text
account_repo
  find_by_id / find_by_username / list_(status, q, page, size)
  insert / update / delete / count_active / touch_last_login

session_repo
  create / find_valid / touch / delete / delete_by_account / purge_expired

report_repo
  insert_draft / find_by_id / update_content / update_generated
  list_(status, q, from, to, mine, page, size) / list_drafts
  next_seq(day) / void / delete

audit_repo
  append(event, actor, target, before, after, result, note)
  list_(from, to, event, actor, result, page, size)
```

### 6.7 为什么 repo 层比"一次把表建全"更重要

1. **表结构一定会变**（这次就从 13 张砍到 5 张）。SQL 关在 repo 里，
   接口层和 service 层一个字都不用改。
2. **加表成本低**：`report_unfit` 这种统计表，将来加回来 = 新增一个 repo 文件 +
   一个迁移版本，不动上层。
3. **可测试**：service 的业务规则（最后一个账号不能停用、编号不复用等）
   可以用一个内存版 repo 替换来测，不需要真数据库。
4. 反过来，如果 SQL 散落在 service / api 里，每加一张表都要翻遍调用点 —— 那才是真的复杂。

## 9. 迁移方案：v0（现状）→ v1（基础版）

### 9.1 原则

1. **先备份**：第一步就是整库备份（用在线备份 API，见 §11.1），失败即中止。
2. **幂等可重跑**：用 `PRAGMA user_version` 判断版本，已是 v1 就跳过。
3. **可回滚**：出问题换回备份文件，不做反向迁移。
4. **先校验后删表**：校验通过前，旧表只改名不删。

### 9.2 步骤

| 步 | 动作 |
| --- | --- |
| 1 | 备份整库 → `backup/pre-migrate-{时间戳}.db`（在线备份 API） |
| 2 | 建 5 张新表与索引（`CREATE TABLE IF NOT EXISTS`，幂等） |
| 3 | `users` → `account`：改名 + 补列；`role` 一律写 `inspector`（含原 admin） |
| 4 | `sessions` → `session`：改名 + 补 `last_seen_at`、`origin` |
| 5 | `report_history` → `report`（字段映射见 §9.3） |
| 6 | `form_draft` → `report`：每个用户一条草稿 → 一条 `status='draft'` 的报告（无编号） |
| 7 | 旧表改名 `*_legacy_20261013`（先不删，保留一个版本） |
| 8 | `PRAGMA user_version = 1` |
| 9 | 校验：行数比对、抽样比对、`PRAGMA integrity_check`、`foreign_key_check` |

### 9.3 `report_history` → `report` 的字段映射

迁移时**重新生成雪花 id**（旧的 1、2、3 与新体系混在一起既难看又破坏"不可枚举"），
旧 id 记进 `provenance_json.legacy_id` 备查。

| 旧字段 | 新字段 |
| --- | --- |
| `id` | `provenance_json.legacy_id` |
| `user_id` | `created_by` |
| `created_at` | `created_at` / `updated_at` |
| `reg` | `form_json.registerNo` |
| `location` | `location` + `form_json.installSite` |
| `form_data` | `form_json` + 6 个提升列（`clientName→client_name` 等） |
| `items_data` | `items_json`（旧结构"编号→状态"统一成 `[{no,result,reasons,other_text}]`） |
| `report_text` | `narrative` |
| `fault_chain` | `provenance_json.kg` |
| — | `report_no`：**按 `created_at` 的日期补号**，并回填 `report_no_seq` |
| — | `status`：有 `report_text` → `generated`；否则 `draft` |
| — | `counters_json`：从 `items_json` 重算 |
| — | `template_version`：写 `JTE-09-R02-3.00` |

**为什么给历史记录补编号**：不补的话老报告在列表里没有编号，现场对不上纸面件；
按创建日期补号不会与将来新发的号冲突（新号从当天流水继续往上走）。

### 9.4 脚本

`backend/tools/migrate_v1.py`：命令行执行、逐步输出、失败非零退出。
上线流程里排在"推后端代码"之后、"重启服务"之前。

## 10. 容量估算与保留策略

### 10.1 容量（按每年 1000 份估算）

| 数据 | 年增量 | 10 年 |
| --- | --- | --- |
| `report` 一行（≈30 KB，含 66 条填写内容） | ≈ 30 MB | ≈ 300 MB |
| `audit_log`（≈200 B × 200 条/天） | ≈ 15 MB | 按 30 天归档后只保留窗口内 |
| `account` / `session` / `report_no_seq` | < 1 MB | < 5 MB |
| **导出产物（PDF/Word，≈1 MB/份）** | **≈ 1 GB** | **≈ 10 GB** |

结论：**库本身很小，吃盘的是导出文件**，所以保留策略的重点在导出目录。

### 10.2 保留策略

| 数据 | 策略 |
| --- | --- |
| 报告记录（已生成/已归档/已作废） | 永久保留 |
| 草稿（`status=draft`） | 保留 90 天，超期在列表里提示清理 |
| 审计日志 | 保留 30 天，之后导出为 CSV/JSON 归档再清除 |
| 导出文件 | 报告删除后可清理；同一报告重复导出只保留最近 3 份 |
| 备份 | 本地保留最近 10 份 |
| 磁盘告警 | 剩余 < 200 MB 时界面告警并写日志 |

## 11. 备份、恢复与完整性

### 11.1 备份怎么做（关键细节）

**不能直接拷 `elevator.db` 文件**：WAL 模式下还有 `-wal` / `-shm`，
直接拷可能拿到"缺了最近事务"的库。用 SQLite 官方的在线备份接口：

```python
import sqlite3
src = sqlite3.connect(DB_PATH)
dst = sqlite3.connect(target_path)
with dst:
    src.backup(dst)      # 一致性快照，不需要停服
dst.close(); src.close()
```

备份目录结构：

```text
backup/20261013-0930/
  elevator.db      # 一致性快照
  export/          # 导出目录（PDF/Word）
  manifest.json    # 文件清单 + 每项 SHA-256
```

（配置快照暂不打包：配置在 `.env` 里，随代码一起管理；等 P1 做了配置界面再纳入。）

### 11.2 恢复流程

1. 校验 `manifest.json` 里每个文件的 SHA-256（不一致直接拒绝，不半途恢复）。
2. **自动备份当前状态**（防"恢复错了回不去"）。
3. 写临时文件 → `os.replace` 原子替换 → 清掉 `-wal` / `-shm` 残留。
4. 跑 `PRAGMA integrity_check` 与 `foreign_key_check`。
5. 提示重启服务（数据库句柄需要重建）。

### 11.3 完整性检查

| 时机 | 检查 | 代价 |
| --- | --- | --- |
| 每次启动 | `PRAGMA quick_check` | 秒级 |
| 每周（systemd timer） | `integrity_check` + `foreign_key_check` | 慢，放空闲时段 |
| 备份后 | 对备份文件跑 `quick_check` | 保证备份可用 |

### 11.4 自动备份

systemd 定时器每天一次，产物落 `/userdata/backup/`，按 §10.2 保留 10 份。
**失败要写审计日志并在界面提示** —— 静默失败的备份等于没有备份。

## 12. 安全

| 项 | 要求 |
| --- | --- |
| 口令 | 只存 `salt + hash`（PBKDF2-HMAC-SHA256）；接口不回传 |
| 登录失败 | 5 次锁定 10 分钟（**内存计数**，重启清零） |
| 会话 | 随机令牌、可吊销、改密/停用即失效、空闲超时 |
| 审计 | 只追加；`actor_name` 冗余快照，账号改名后日志仍准 |
| 文件权限 | 数据库 640、数据目录 750、`.env` 600、`recovery.key` 600（部署脚本负责） |
| 备份文件 | 含口令哈希，权限同数据库；U 盘备份后提醒妥善保管 |
| 路径白名单 | 导出目录之外的文件不允许被"打开文件"接口访问 |
| 数据分级 | 报告含使用单位名称等业务数据；系统不采集个人隐私字段 |
| 不做的 | 不引入 SQLCipher 等加密库（板端装不了）；按"设备物理可控"的信任模型处理，交付文档里写明 |
