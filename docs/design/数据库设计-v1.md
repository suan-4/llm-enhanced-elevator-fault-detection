## 1. 设计原则与约束

### 1.1 板端硬约束（决定了技术选型）

| 约束 | 影响 |
| --- | --- |
| 板端离线，apt / pip 不可用，新依赖要预置 aarch64 wheel | 只用 Python 标准库 `sqlite3`，**不引入 ORM、不引入 Alembic** |
| 单机、低并发（一个人用一个终端） | 无需连接池；短连接 + 事务即可 |
| 断电是常态（现场拔电、板子直接断电） | 必须开 WAL、写入要原子、备份要能恢复 |
| 磁盘是板载 eMMC，寿命有限 | 控制写入频率（草稿防抖 800ms）、日志轮转、旧数据定期归档 |
| 知识图谱在 Neo4j | 业务库**不复制**图谱内容，只存报告引用到的节点 id 与摘要 |

### 1.2 为什么是 SQLite（而不是别的）

1. **零依赖**：标准库自带，板端不需要装任何东西。
2. **单文件 + 单进程**：备份就是拷文件，恢复就是换文件，现场可操作。
3. **事务够用**：一个人用的系统，写冲突几乎不存在。
4. 数据量小：估算见 §8，十年数据也就几百 MB。

### 1.3 命名与类型约定

| 约定 | 说明 |
| --- | --- |
| 表名 | 单数名词、小写下划线：`account`、`report`、`audit_log` |
| 时间列 | 一律 `_at` 后缀，值为本地时间字符串 `YYYY-MM-DDTHH:MM:SS` |
| 日期列 | 一律 `_on` 后缀（如 `assessed_on`），值为 `YYYY-MM-DD` |
| 布尔列 | `is_` 前缀或含义自明，值用 `INTEGER` 0/1 |
| JSON 列 | `_json` 后缀，值为 JSON 文本（UTF-8，不转义中文） |
| 主键 | 业务表统一用**雪花 ID**：`id INTEGER PRIMARY KEY`（不带 `AUTOINCREMENT`，由应用生成）；关联表用复合主键；业务键另建唯一索引。详见 §5 |
| 外键 | 一律显式声明并开 `PRAGMA foreign_keys=ON`。**审计表例外**（见 §4.10） |

### 1.4 JSON 的使用边界

JSON 只用于**整存整取的文档型内容**，且必须满足"这一坨永远一起读、一起写"：

- 适用：报告的抬头全量字段、66 条填写内容、风险评定值映射。
- 不适用：需要筛选 / 排序 / 统计的字段 —— 这类一律提升为真实列
  （例如 `client_name`、`report_no`、`assessed_on`）。

这条边界的意义：SQLite 查 JSON 得用 `json_extract`，写起来麻烦、索引支持也弱，
所以**凡是查询条件里会出现的字段，都不许留在 JSON 里**。

### 1.5 数据库级 PRAGMA

连接建立时统一设置（写在 `db.py` 的取连接函数里）：

```sql
PRAGMA journal_mode = WAL;      -- 断电更安全，读写不互斥
PRAGMA synchronous  = FULL;     -- 板端断电频繁，宁可慢一点也不能丢已提交数据
PRAGMA foreign_keys = ON;       -- 外键真的生效（SQLite 默认是关的）
PRAGMA busy_timeout = 10000;    -- 等锁 10 秒，避免瞬时 500
PRAGMA temp_store   = MEMORY;
```

## 2. 现状盘点

现有库（`backend/app/db.py`）只有 4 张表，都是跟着旧版单文件前端临时长出来的：

| 现有表 | 用途 | 问题 |
| --- | --- | --- |
| `users` | 账号 | 有 `role` 字段但实际只用 admin/inspector；缺 `employee_no`、`must_change_password`、停用时间与操作者 |
| `sessions` | 登录令牌 | 缺 `last_seen_at`（做不了空闲超时）与来源 |
| `report_history` | 报告历史 | 只有"提交后的结果"，**没有状态机**（草稿/已生成/已归档/已作废分不出来）、**没有报告编号**、**没有风险评定值与得分等级**、明细混在 JSON 里且无版本 |
| `form_draft` | 每人一份草稿 | **每人只能有一份**，跨电梯复用 —— 这正是旧版"上一条电梯的判定被误当本次结果"的根源 |

另外缺失、但 PRD 已要求的能力：审计日志、系统配置、配置变更历史、导出文件登记、
登录失败锁定、口令历史、编号流水、条目库版本。

因此 v1 不是"补两张表"，而是**按报告全生命周期重构**：
一条 `report` 记录从草稿一路走到归档，`report_history` 与 `form_draft` 都并入它。

## 4. 表结构详设

### 4.0 报告的两套标识（先说清楚，后面所有表都按这个来）

| 标识 | 字段 | 例子 | 用途 | 用户可见 |
| --- | --- | --- | --- | --- |
| 内部主键 | `id`（雪花 ID，64 位整数） | `532918374650120192` | 表间关联（`report_file` / `report_unfit`）、接口路径 `/api/reports/{id}` | 否 |
| 业务编号 | `report_no`（TEXT） | `GDSEI-JTE-20261013-001` | 印在报告上、归档、口头引用 | 是 |

为什么不用业务编号当主键（三条都是硬理由）：

1. **草稿阶段还没有编号** —— 编号在"生成报告"时才分配，而主键必须一建记录就有。
2. **机构可能改编号规则**，已经发出去的报告必须保住旧号，主键不能随规则变。
3. **作废号不复用** → 业务编号天然会断号；主键不断号，做索引与外键更省事。

为什么内部主键用雪花 ID，而不是 1、2、3 自增（2026-10-13 决定）：

1. **为多台终端留路**：PRD Q8 还没定"现场一台还是一批"。自增 id 一旦上第二台必然撞号，
   届时要么改号、要么合并库，都是手术；雪花 ID 天生不撞，不需要这一步。
2. **应用侧生成，插入前就有 id**：便于"先建报告再挂明细"的写法，也让接口重试天然幂等。
3. **不可枚举**：自增 id 会泄露"机构一共做过多少份报告"，雪花 ID 不会。

代价与对策（两条都必须落进实现，见 §5）：

1. **时钟依赖**：本机 RTC 不可信（开机会回到 2021-01-01）。对策：雪花 ID 里的时间戳
   **不当业务时间用**（业务时间另有 `created_at` / `generated_at` / `assessed_on` 字段），
   生成器必须处理时钟回拨；并且**报告编号走 `report_no`（按日流水），与雪花 ID 无关** ——
   即便时钟是错的，报告编号也不受影响。
2. **JS 精度**：雪花 ID 超出 `Number.MAX_SAFE_INTEGER`（2^53-1），在浏览器里会失真。
   对策：**JSON 里的 id 一律用字符串**（`"id": "532918374650120192"`），
   前端与 URL 也用字符串；Python / SQLite 侧仍是 64 位整数。

界面呈现约定：

- 已生成 / 已归档 / 已作废：显示 `report_no`。
- 草稿：**没有正式编号**，列表里显示「草稿 · 创建时间」，链接仍用 `id`；
  不把内部 id 当编号展示给用户（避免"报告号是个 12"的观感）。

### 4.1 `schema_version` —— 迁移版本

```sql
CREATE TABLE IF NOT EXISTS schema_version (
  version    INTEGER PRIMARY KEY,
  applied_at TEXT NOT NULL,
  note       TEXT NOT NULL DEFAULT ''
);
```

每次结构变更一个版本号，迁移脚本按版本号顺序、幂等地执行（见 §7）。
启动时对比"代码期望版本"与"库里版本"，不一致就拒绝启动并提示执行迁移 ——
避免用旧结构跑新代码导致的隐性数据错误。

### 4.2 `account` —— 账号

```sql
CREATE TABLE IF NOT EXISTS account (
  id                   INTEGER PRIMARY KEY,            -- 雪花 ID（§5）
  username             TEXT    NOT NULL,               -- 登录名，创建后不可改
  display_name         TEXT    NOT NULL,               -- 姓名，进报告与留痕
  employee_no          TEXT    NOT NULL DEFAULT '',    -- 工号（可空）
  password_salt        TEXT    NOT NULL,
  password_hash        TEXT    NOT NULL,
  password_algo        TEXT    NOT NULL DEFAULT 'pbkdf2_sha256$120000',  -- 便于将来升级迭代次数
  role                 TEXT    NOT NULL DEFAULT 'inspector',             -- 恒为 inspector，预留扩展
  is_active            INTEGER NOT NULL DEFAULT 1,
  must_change_password INTEGER NOT NULL DEFAULT 0,     -- 开户/重置时勾"要求首登改密"
  created_at           TEXT    NOT NULL,
  created_by           INTEGER REFERENCES account(id), -- 首次初始化时为 NULL
  last_login_at        TEXT,
  disabled_at          TEXT,
  disabled_by          INTEGER REFERENCES account(id)
);

CREATE UNIQUE INDEX IF NOT EXISTS ux_account_username ON account(username);
CREATE INDEX        IF NOT EXISTS ix_account_active   ON account(is_active);
```

要点：

1. `username` **唯一且不可修改** —— 历史报告的责任人要能对上。
2. 只停用不删除：删除账户会让历史报告失去责任人。真要删除时由业务层校验"无报告才允许"。
3. `password_algo` 存"算法+迭代次数"，将来提高迭代次数时可渐进升级，不用一次性重算所有人。
4. 保留 `role` 字段但恒为 `inspector`：单角色是当前决定，字段留着将来不必改表。

### 4.3 `login_attempt` —— 登录失败与锁定

```sql
CREATE TABLE IF NOT EXISTS login_attempt (
  username       TEXT    PRIMARY KEY,     -- 用输入的用户名，防枚举：不存在也计数
  failed_count   INTEGER NOT NULL DEFAULT 0,
  last_failed_at TEXT,
  locked_until   TEXT
);
```

规则：连续 5 次失败写 `locked_until = now + 10min`；登录成功清零。
保留策略：记录数上限=账号数级别，无需清理；`locked_until` 过期后按需清空。

### 4.4 `password_history` —— 口令历史

```sql
CREATE TABLE IF NOT EXISTS password_history (
  id            INTEGER PRIMARY KEY,       -- 雪花 ID（§5）
  account_id    INTEGER NOT NULL REFERENCES account(id) ON DELETE CASCADE,
  password_salt TEXT NOT NULL,
  password_hash TEXT NOT NULL,
  created_at    TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS ix_pwd_hist_account ON password_history(account_id, id DESC);
```

用途：改密时校验"不得与前 3 次重复"。每次改密后只保留最近 3 条（由业务层裁剪）。

### 4.5 `session` —— 登录令牌

```sql
CREATE TABLE IF NOT EXISTS session (
  token        TEXT    PRIMARY KEY,       -- secrets.token_urlsafe(32)
  account_id   INTEGER NOT NULL REFERENCES account(id) ON DELETE CASCADE,
  created_at   TEXT    NOT NULL,
  expires_at   TEXT    NOT NULL,
  last_seen_at TEXT,                      -- 空闲超时判断
  origin       TEXT    NOT NULL DEFAULT ''-- 来源（回环地址标记），供审计
);

CREATE INDEX IF NOT EXISTS ix_session_account ON session(account_id);
CREATE INDEX IF NOT EXISTS ix_session_expires ON session(expires_at);
```

要点：

1. 改密、停用、重置口令 → 删除该账号全部会话（`ON DELETE CASCADE` 兜住删账号的情况）。
2. 空闲超时：`last_seen_at` 超过 `session_ttl_hours` 即视为过期；启动与登录时顺带清理过期会话。

### 4.6 `report` —— 报告主表

```sql
CREATE TABLE IF NOT EXISTS report (
  id              INTEGER PRIMARY KEY,                    -- 雪花 ID（§5）
  report_no       TEXT,                                   -- 草稿为 NULL，生成时分配
  status          TEXT    NOT NULL DEFAULT 'draft',       -- draft|generated|filed|void
  version         INTEGER NOT NULL DEFAULT 1,             -- 每次重新生成 +1
  created_by      INTEGER NOT NULL REFERENCES account(id),
  created_at      TEXT    NOT NULL,
  updated_at      TEXT    NOT NULL,
  generated_at    TEXT,
  exported_at     TEXT,
  voided_at       TEXT,
  void_reason     TEXT    NOT NULL DEFAULT '',

  -- 抬头里需要筛选/排序的字段，从 form_json 提升为真实列
  client_name     TEXT    NOT NULL DEFAULT '',            -- 委托单位名称
  user_name       TEXT    NOT NULL DEFAULT '',            -- 使用单位名称
  device_category TEXT    NOT NULL DEFAULT '',            -- 设备类别
  product_no      TEXT    NOT NULL DEFAULT '',            -- 产品编号
  location        TEXT    NOT NULL DEFAULT '',            -- 安装地点
  assessed_on     TEXT    NOT NULL DEFAULT '',            -- 评估日期 YYYY-MM-DD

  -- 内容（整存整取）
  form_json       TEXT    NOT NULL DEFAULT '{}',          -- 抬头 21 个字段全量
  items_json      TEXT    NOT NULL DEFAULT '[]',          -- 66 条填写内容
  counters_json   TEXT    NOT NULL DEFAULT '{}',          -- {total,done,unfit,missing}
  risks_json      TEXT    NOT NULL DEFAULT '{}',          -- { "1.7": RiskValue }
  score           INTEGER,                                -- 综合安全状况得分 G
  grade           TEXT,                                   -- 一级/二级/三级/四级
  narrative       TEXT    NOT NULL DEFAULT '',            -- 叙述性文字（大模型或兜底摘要）
  provenance_json TEXT    NOT NULL DEFAULT '{}',          -- 图谱链路/规则命中/是否用模型/耗时

  -- 追溯
  catalog_version TEXT    NOT NULL DEFAULT '',            -- 生成时使用的条目库版本
  template_version TEXT   NOT NULL DEFAULT ''             -- 模板版本（如 JTE-09-R02-3.00）
);

-- 编号唯一且不回退：草稿允许为空，故用部分唯一索引
CREATE UNIQUE INDEX IF NOT EXISTS ux_report_no      ON report(report_no) WHERE report_no IS NOT NULL;
CREATE INDEX        IF NOT EXISTS ix_report_created ON report(created_at DESC);
CREATE INDEX        IF NOT EXISTS ix_report_status  ON report(status, created_at DESC);
CREATE INDEX        IF NOT EXISTS ix_report_creator ON report(created_by, created_at DESC);
CREATE INDEX        IF NOT EXISTS ix_report_client  ON report(client_name);
CREATE INDEX        IF NOT EXISTS ix_report_on      ON report(assessed_on);
```

状态与字段的对应关系（服务端必须保证一致）：

| 状态 | `report_no` | `generated_at` | `exported_at` | 说明 |
| --- | --- | --- | --- | --- |
| `draft` 草稿 | 可空 | 空 | 空 | 只保存填写内容 |
| `generated` 已生成 | 必填 | 必填 | 空 | 已算出风险评定值与 G |
| `filed` 已归档 | 必填 | 必填 | 必填 | 已导出并登记 `report_file` |
| `void` 已作废 | 保留原值 | 保留 | 保留 | `void_reason` 必填，编号不复用 |

要点：

1. **草稿保存全部状态**（抬头 + 66 条勾选 + 情形 + 其他文字）—— 2026-10-13 决定。
   旧版"不保存勾选"是为了绕开"每人一个全局草稿槽跨电梯复用"的问题；
   现在一份评估就是一条记录，新建评估 = 插入一条空白记录，问题从模型上消失。
2. 已生成的报告被修改 → 由服务端把 `status` 回落为 `draft`、`version + 1`，
   旧的风险值保留在 `risks_json` 里直到重新生成覆盖（便于对比"改了什么"）。
3. `client_name` 等 6 列是 `form_json` 的**投影**，由服务端在保存时同步写入，
   禁止只改 JSON 不改列（写在同一个函数里，见 §6.3）。

### 4.7 `report_unfit` —— 不符合项投影

```sql
CREATE TABLE IF NOT EXISTS report_unfit (
  report_id   INTEGER NOT NULL REFERENCES report(id) ON DELETE CASCADE,
  item_no     TEXT    NOT NULL,              -- 项目编号，如 1.7
  item_name   TEXT    NOT NULL DEFAULT '',
  category    TEXT    NOT NULL DEFAULT '',   -- 风险类别 Ⅰ/Ⅱ/Ⅲ
  severity    INTEGER,
  probability TEXT,
  PRIMARY KEY (report_id, item_no)
);

CREATE INDEX IF NOT EXISTS ix_unfit_item     ON report_unfit(item_no);
CREATE INDEX IF NOT EXISTS ix_unfit_category ON report_unfit(category);
```

为什么单独一张表：P2 要做"不符合项分布/风险类别统计"，
用 `json_each` 遍历 66 条太别扭。这张表是**投影**，可在生成报告时写入、
也可从 `items_json` 全量重算（重算脚本随设计一并提供）。

### 4.8 `report_file` —— 导出产物

```sql
CREATE TABLE IF NOT EXISTS report_file (
  id         INTEGER PRIMARY KEY,            -- 雪花 ID（§5）
  report_id  INTEGER NOT NULL REFERENCES report(id) ON DELETE CASCADE,
  fmt        TEXT    NOT NULL,               -- pdf | docx
  filename   TEXT    NOT NULL,
  path       TEXT    NOT NULL,               -- 绝对路径（限制在导出目录内）
  size       INTEGER NOT NULL DEFAULT 0,
  sha256     TEXT    NOT NULL DEFAULT '',
  created_at TEXT    NOT NULL,
  created_by INTEGER REFERENCES account(id)
);

CREATE INDEX IF NOT EXISTS ix_file_report ON report_file(report_id, id DESC);
```

重复导出不覆盖旧文件（文件名追加序号），因此这里一对多。
删除报告时文件记录随之删除，但**磁盘文件不自动删**（避免误删已交付的产物），
由"清理导出目录"功能显式处理。

### 4.9 `report_no_seq` —— 编号按日流水

```sql
CREATE TABLE IF NOT EXISTS report_no_seq (
  day      TEXT    PRIMARY KEY,              -- YYYYMMDD
  last_seq INTEGER NOT NULL DEFAULT 0
);
```

编号规则（2026-10-13 定）：`{机构前缀}-{YYYYMMDD}-{3 位流水}`，
默认前缀 `GDSEI-JTE`（配置项 `report_no_prefix`），例如 `GDSEI-JTE-20261013-001`。

分配逻辑必须在一个事务里完成，否则并发下会撞号：

```sql
BEGIN IMMEDIATE;
  INSERT INTO report_no_seq(day, last_seq) VALUES (:day, 0)
    ON CONFLICT(day) DO UPDATE SET last_seq = last_seq + 1;
  SELECT last_seq FROM report_no_seq WHERE day = :day;   -- 拿到本次号
  UPDATE report SET report_no = :no, status='generated', generated_at = :now WHERE id = :id;
COMMIT;
```

要点：

1. 流水**只增不减**，作废的号不回填，保证编号永不复用。
2. 按日重置，一天最多 999 份；超过 3 位自然进位（不截断）。
3. 完整时间戳（`created_at` / `generated_at` / `assessed_on`）单独保存，
   编号只承担"唯一标识 + 当天可读"。

### 4.10 `audit_log` —— 审计日志

```sql
CREATE TABLE IF NOT EXISTS audit_log (
  id          INTEGER PRIMARY KEY,           -- 雪花 ID（§5）
  at          TEXT NOT NULL,
  actor_id    INTEGER,                       -- 故意不加外键，见下
  actor_name  TEXT NOT NULL DEFAULT '',      -- 冗余快照
```

## 5. ID 生成：雪花算法

### 5.1 位分配

标准 64 位布局，共 63 位可用：

| 位 | 段 | 值域 | 说明 |
| --- | --- | --- | --- |
| 1 | 符号位 | 恒 0 | 保证是正数 |
| 41 | 毫秒时间戳 | 相对自定义纪元的毫秒数 | 41 位 ≈ 69 年 |
| 10 | 工作节点 id | 0~1023 | 一台终端一个值（配置项 `worker_id`，默认 1） |
| 12 | 同毫秒序号 | 0~4095 | 单节点每毫秒最多 4096 个 id，够用 |

自定义纪元取 `2026-01-01 00:00:00 +08:00`（`EPOCH_MS = 1767225600000`）：
把纪元设在系统投用前后，可以在 69 年的时间跨度里塞进更多可用位。

### 5.2 为什么这套在当前场景够用

- 单节点每毫秒 4096 个 id，本系统的写入频率是"一分钟几份报告"，连零头都用不到。
- 按时间递增 → 主键索引顺序写入，不会像随机 id 那样造成页分裂。
- 工作节点位留了 1024 个位置，将来真上多台终端也不用改结构、不用合并数据。

### 5.3 时钟回拨与重启保护（这块是本项目的重点）

板端 RTC 不可信（开机会回到 2021-01-01），所以必须假设"时钟会乱跳"。三道防线：

1. **启动时用库里最大 id 反推时间戳当下界**：id 里就编码了时间戳，
   所以 `last_ms = (MAX(id) >> 22) + EPOCH_MS`。这样即使开机时钟是 2021 年，
   生成器也会从"上次发到哪儿"继续往前，不会倒退、不会重复。**这是最关键的一道。**
2. **运行期小幅回拨**（≤ 5 ms）：等一小会儿再发，保证不重复。
3. **运行期大幅回拨**：直接抛错，拒绝生成 id 并提示校时 ——
   宁可让报告生成失败（可重试），也绝不发重复 id。

另外重申：**id 里的时间戳不参与任何业务时间**。报告时间一律看
`created_at` / `generated_at` / `assessed_on`，它们由 NFR 6.4 的校时策略保证。

### 5.4 参考实现（Python 标准库，无第三方依赖）

```python
"""雪花 ID 生成器。板端零依赖：只用 threading + time。"""
import threading
import time

EPOCH_MS = 1767225600000          # 2026-01-01 00:00:00 +08:00
WORKER_BITS, SEQ_BITS = 10, 12
WORKER_SHIFT = SEQ_BITS
TIME_SHIFT = SEQ_BITS + WORKER_BITS
SEQ_MASK = (1 << SEQ_BITS) - 1


class Snowflake:
    def __init__(self, worker_id: int, last_ms: int = 0) -> None:
        if not 0 <= worker_id < (1 << WORKER_BITS):
            raise ValueError("worker_id 必须落在 0~1023")
        self.worker_id = worker_id
        self._lock = threading.Lock()
        self._last_ms = last_ms      # 由 MAX(id) 反推而来，见 §5.3
        self._seq = 0

    def next_id(self) -> int:
        with self._lock:
            now = int(time.time() * 1000)
            if now < self._last_ms:
                gap = self._last_ms - now
                if gap > 5:
                    raise RuntimeError("系统时间被回拨，拒绝生成 ID，请先校时")
                time.sleep(gap / 1000)
                now = int(time.time() * 1000)
            if now == self._last_ms:
                self._seq = (self._seq + 1) & SEQ_MASK
                if self._seq == 0:                      # 同毫秒 4096 个用满，等下一毫秒
                    while now <= self._last_ms:
                        now = int(time.time() * 1000)
            else:
                self._seq = 0
            self._last_ms = now
            return ((now - EPOCH_MS) << TIME_SHIFT) | (self.worker_id << WORKER_SHIFT) | self._seq


def restore_last_ms(max_id: int | None) -> int:
    """启动时从库里最大 id 反推上次时间戳，避免时钟回拨造成重复 id。"""
    return 0 if not max_id else (max_id >> TIME_SHIFT) + EPOCH_MS
```

接入方式：进程启动时 `SELECT MAX(id) FROM ...` 各业务表取全局最大值 → `restore_last_ms` →
构造单例生成器；所有 `INSERT` 显式带上生成的 id。

### 5.5 传输与序列化约定（不做这条一定出 bug）

雪花 ID 是 19 位十进制数，**超出 JS 的 `Number.MAX_SAFE_INTEGER`**，浏览器里会失真
（例如 `532918374650120192` 变成 `532918374650120200`，再去请求就是 404）。

| 层 | 类型 | 说明 |
| --- | --- | --- |
| Python | `int` | 原生大整数，无问题 |
| SQLite 列 | `INTEGER`（64 位） | 雪花 ID 在 int64 范围内，可直接做主键 |
| **JSON / 接口** | **string** | 所有响应里的 `id` 必须是字符串；请求路径与参数也按字符串接收 |
| 前端 | `string` | 不做数值运算，只做等值比较与拼接 |
| 日志 | string | 打印时保持原样 |

即：`{ "id": "532918374650120192" }`，不是 `{ "id": 532918374650120192 }`。

### 5.6 验收（写进测试）

1. **不重复**：单线程连续生成 100 万个，无重复；多线程（8 线程 × 10 万）无重复。
2. **递增**：同毫秒内序号递增，跨毫秒时间戳递增。
3. **时钟回拨**：把系统时间往前调 1 小时，必须抛错而不是发出重复 id。
4. **重启**：生成一批 id、记录最大值、模拟时钟回到 2021 年再重启，
   新生成的 id 必须大于旧的最大值。
5. **端到端**：接口返回的 `id` 是字符串，前端拿到后能原样用于 `GET /api/reports/{id}`。

## 8. 迁移方案：v0（现状）→ v1（目标）

### 8.1 前置与原则

1. **先备份**：迁移脚本第一步就是整库备份（用 SQLite 在线备份 API，见 §10.1），失败即中止。
2. **幂等可重跑**：按 `schema_version` 判断该不该执行，重复执行直接跳过。
3. **可回滚**：出问题就换回备份文件，不做"反向迁移"。
4. **先校验后删表**：新表数据校验通过之前，旧表只改名不删除。

### 8.2 步骤

| 步 | 动作 | 说明 |
| --- | --- | --- |
| 1 | 备份整库 → `backup/pre-migrate-{时间戳}.db` | 用在线备份 API，保证 WAL 下一致 |
| 2 | 建全部新表与索引（`CREATE TABLE IF NOT EXISTS`） | 幂等 |
| 3 | `users` → `account` | 改名 + 补列（`employee_no`、`must_change_password`、`disabled_at`、`disabled_by`、`created_by`、`password_algo`）；`role` 一律写 `inspector`（含原来的 admin） |
| 4 | `sessions` → `session` | 改名 + 补列（`last_seen_at`、`origin`） |
| 5 | `report_history` → `report` | 见 §8.3 字段映射 |
| 6 | `form_draft` → `report` | 每个用户一条草稿 → 生成一条 `status='draft'` 的报告（无编号） |
| 7 | 旧表改名 `*_legacy_20261013` | 先不删，保留一个版本 |
| 8 | 写 `schema_version = 1`、`app_config` 默认值、`item_catalog_version` | |
| 9 | 校验：行数比对、抽样比对、`PRAGMA integrity_check`、`PRAGMA foreign_key_check` | 任一不过 → 中止并提示恢复备份 |

### 8.3 `report_history` → `report` 的字段映射

迁移时**重新生成雪花 id**（旧的 1、2、3 与新体系混在一起既难看又破坏"不可枚举"），
旧 id 记到 `provenance_json.legacy_id` 里以备追溯。

| 旧字段 | 新字段 | 说明 |
| --- | --- | --- |
| `id` | `provenance_json.legacy_id` | 只作追溯 |
| `user_id` | `created_by` | |
| `created_at` | `created_at` / `updated_at` | |
| `reg` | `form_json.registerNo` | 使用登记证编号 |
| `location` | `location` + `form_json.installSite` | 提升列同时保留进 JSON |
| `form_data` | `form_json` + 6 个提升列 | `clientName→client_name`、`userName→user_name`、`deviceCategory→device_category`、`productNo→product_no`、`installSite→location`、`assessDate→assessed_on` |
| `items_data` | `items_json` | 旧结构是"编号→状态"，迁移时统一成 `[{no,result,reasons,other_text}]` |
| `report_text` | `narrative` | |

## 9. 容量估算与保留策略

### 9.1 容量

以每年 1000 份评估估算：

| 数据 | 单条大小 | 年增量 | 10 年 |
| --- | --- | --- | --- |
| `report` 一行 | ≈ 30 KB（66 条填写内容约占 13 KB） | ≈ 30 MB | ≈ 300 MB |
| `report_unfit` | 几十字节 × 不符合项 | < 1 MB | < 5 MB |
| `audit_log` | ≈ 200 B × 200 条/天 | ≈ 15 MB | ≈ 150 MB（按 30 天归档后仅保留窗口内） |
| `report_file`、`session`、`account` | 很小 | < 1 MB | < 5 MB |
| **导出产物（PDF/Word）** | ≈ 1 MB/份 | **≈ 1 GB** | **≈ 10 GB** |

结论：**数据库本身很小（十年几百 MB），真正吃盘的是导出文件**。
所以保留策略的重点在导出目录，而不是库。

### 9.2 保留策略（与 PRD §7.3 一致）

| 数据 | 策略 |
| --- | --- |
| 报告记录（已生成/已归档/已作废） | 永久保留 |
| 草稿（`status=draft`） | 保留 90 天（`history_keep_days`），超期在列表里提示清理 |
| 审计日志 | 保留 30 天（`audit_keep_days`），之后导出为 CSV/JSON 文件归档后清除 |
| 导出文件 | 报告删除后可清理；同一报告重复导出只保留最近 3 份 |
| 备份 | 本地保留最近 10 份，超出按时间删除 |
| 磁盘告警 | 剩余 < 200 MB 时界面告警并写日志 |

## 10. 备份、恢复与完整性

### 10.1 备份怎么做（关键细节）

**不能用"直接拷 `elevator.db` 文件"的方式备份**：WAL 模式下还有 `-wal` / `-shm` 文件，
直接拷文件可能拿到"缺了最近事务"的库。正确做法是用 SQLite 官方的在线备份接口：

```python
import sqlite3
src = sqlite3.connect(DB_PATH)
dst = sqlite3.connect(target_path)
with dst:
    src.backup(dst)      # 一致性快照，不需要停服
dst.close(); src.close()
```

备份产物目录结构：

```text
backup/20261013-0930/
  elevator.db          # 一致性快照
  export/              # 导出目录（PDF/Word）
  config.json          # app_config 快照
  catalog.json         # 条目库版本信息
  manifest.json        # 文件清单 + 每项 SHA-256
```

### 10.2 恢复流程

1. 校验 `manifest.json` 里每个文件的 SHA-256（不一致直接拒绝，不半途恢复）。
2. **自动备份当前状态**（防止"恢复错了回不去"）。
3. 写临时文件 → 原子替换（`os.replace`）→ 删除 `-wal` / `-shm` 残留。
4. 跑 `PRAGMA integrity_check` 与 `PRAGMA foreign_key_check`。
5. 提示重启服务（数据库句柄需要重建）。

### 10.3 完整性检查

| 时机 | 检查 | 代价 |
| --- | --- | --- |
| 每次启动 | `PRAGMA quick_check` | 快，秒级 |
| 每周（systemd timer） | `PRAGMA integrity_check` + `foreign_key_check` | 慢，放在空闲时段 |
| 备份后 | 对备份文件跑 `quick_check` | 保证备份可用 |

### 10.4 自动备份

`systemd` 定时器每天一次（放在夜里），产物落到 `/userdata/backup/`，按 §9.2 保留 10 份。
备份失败要写审计日志并在界面顶部提示 —— 静默失败的备份等于没有备份。

## 11. 安全

| 项 | 要求 |
| --- | --- |
| 口令 | 只存 `salt + hash`（PBKDF2-HMAC-SHA256）；接口不回传；`password_algo` 便于将来提升迭代次数 |
| 口令历史 | 最近 3 次，禁止重复使用 |
| 登录失败 | 5 次锁定 10 分钟（`login_attempt`） |
| 会话 | 令牌随机、可吊销、改密/停用即失效；空闲超时 |
| 审计 | 只追加，不在界面提供删除入口；`actor_name` 冗余快照，账号改名后日志仍准 |
| 文件权限 | 数据库 640、数据目录 750、`.env` 600、`recovery.key` 600（部署脚本负责设置） |
| 备份文件 | 含口令哈希，权限同数据库；U 盘备份后提醒妥善保管 |
| 路径白名单 | 导出目录之外的文件不允许被"打开文件"接口访问 |
| 数据分级 | 报告中含使用单位名称等信息，属业务数据；系统不采集个人隐私字段 |
| 不做的 | 不引入 SQLCipher 等加密库（板端装不了）；按"设备物理可控"的信任模型处理，并在交付文档里写明 |
